# §16 模型之外还要配些什么？——工具调用、记忆与评估 ▽

模型在真实任务里出错，问题常在系统结构，补也要从结构入手。能力之外，模型还要配哪些工程件？它们围着一个循环怎么转、各自补哪个缺口？

给“模型外面的工程系统”一个名字：**Harness**。工程里常把它定义成模型之外、把模型能力接到任务上的一切：工具、上下文、编排、评估、护栏。一句话：Agent = 模型 + Harness。模型负责在每一步做判断，Harness 负责让判断能变成动作、动作有反馈、反馈能回到下一步。

## 最小形状与数据流：一个循环怎么转

最小形状是一个循环：模型读当前上下文，选一个动作；系统执行动作，把结果写回上下文；模型再读、再选，直到停止。工具负责“做”，上下文与记忆负责“给模型看什么”，编排负责“循环怎么走、何时停”，评估与护栏横切每一步。后面这六件事说的是整个 Agent：模型调用是循环的核心，另外五件在模型外面——这五件合起来，正是 Harness 包揽的部分。

| 角色 | 管什么 | 在循环里的位置 | 一个工程动作 | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| 模型调用 | 读上下文，选下一步动作 | 循环的核心 | 接一个 OpenAI 兼容端点（按 GPT 开发商 OpenAI 的 API 格式提供服务的接口地址） | 没有判断，只剩固定脚本 |
| 工具与协议 | 把动作接到外部世界 | 动作 | 注册一个带 schema（参数的结构声明）的工具 | 只能空谈，碰不到数据与系统 |
| 上下文与记忆 | 决定模型每一步看到什么 | 观测到判断之间 | 把会话日志、检索结果、工具返回装进窗口 | 模型看不见关键信息，或看见太多噪声 |
| 编排 | 控制循环节奏与停止 | 循环外层 | 设最大步数、重试与升级规则 | 死循环，或该停不停 |
| 评估与观测 | 判断这一步、这一轮做对没有 | 横切每一步 | 记录轨迹，跑验收与回归（防改动把以前能对的改坏） | 不知道哪一步走偏 |
| 护栏与权限 | 决定动作能不能生效 | 横切每一步 | 给动作过一道权限门 | 越界动作造成不可逆伤害 |

六项是分工，不是层级。评估与护栏不站在顶上，它们横切每一步；编排也不在模型之上，它决定循环怎么转。简单的单步任务，模型调用加工具就够；其余几件按失效点补，不按资历补。

〔图 16-1：Agent 的最小形状——模型调用在循环中心；工具把动作接到外部世界，上下文与记忆把观测带回模型；编排控制循环，评估与护栏横切每一步。六件事是分工，不是层级。〕

§15 的七元组（POMDP 那七个组成部分），工程上能对上号的是四件：策略 π 是模型调用——给定信念 bₜ，选动作；信念 bₜ 由上下文与记忆维护；动作 aₜ 由工具执行；返回 oₜ₊₁ 是观测。编排不在七元组里，工程上要补这一位：它决定循环何时继续、何时停、何时升级给人。其余几位（状态转移、折扣、奖励）是数学模型自己的账，不落在工程件上。七元组描述流程，六件事是它的工程分工。

这六件事没有统一的行业分层。模型调用与工具协议已有可直接使用的方案；上下文、记忆与编排仍在快速变化；评估与护栏是最容易省略、也最该先补的两件事（截至 2026 年 10 月）。

六件事怎么转起来？把一个回路画成一条箭头链：

    oₜ —上下文与记忆→ bₜ —模型调用→ aₜ —工具→ oₜ₊₁

四个符号各是什么。oₜ 是观测，用户输入、工具返回、报错，都是模型能看到的东西；bₜ 是信念状态——对各状态可能性的一张打分表（§15 用手算走过一遍），由上下文与记忆维护；aₜ 是动作，搜索、写代码、调 API，由工具执行（aₜ 的 a 是动作 action；支线 T2 里另有一个同名的 a_t，读到那里别认混）；oₜ₊₁ 是新观测，动作之后的下一轮。

编排不在箭头链上：它控制整个循环的节奏——何时调用模型、何时重试、何时中断、何时升级给人。

〔图 16-2：Agent Loop 运行时剖面——观测、信念、动作、新观测四盒的箭头链，外层编排框与三种停止信号；示意图，非实测。〕

一个编码 Agent 修 bug，前两轮没改对，第三轮的表长这样（教学推演，表内阈值与文件名均为设定）：

| 这一步谁出力 | 这一轮做什么 | 具体数据 |
| --- | --- | --- |
| 评估与观测 | 读出测试失败 | `failed test_parse_date` |
| 上下文与记忆 | 组装上下文 | 任务、失败计数、最近一次改动 |
| 模型调用 | 判断病因 | 是日期格式串写错 |
| 护栏与权限 | 过安全门 | 风险分 0.2（设定值），低于示例阈值 0.7，放行 |
| 工具 | 执行改动 | `edit_file(utils.py, 格式串)` |
| 编排 | 调度下一轮 | 重跑测试 |

表里的 0.7 是示例阈值；A_safe(c) 是给定当前上下文 c 时允许生效的动作集合。一个反例：如果上下文与记忆丢了历史，忘了第一轮已经改过格式串，模型可能再改一次。循环在原地转，两轮白跑。

## 协议与契约：工具怎么接 ▽

工具怎么接到模型上？先分清两样东西。协议是信道与握手规范，会换代；契约是工具自己的义务清单，换协议换不掉。**MCP**（Model Context Protocol，模型上下文协议）管 Agent 与工具之间的连接：传输格式与握手。具体声明什么、校验什么、返回什么，仍由契约规定。Agent 与 Agent 之间怎么协作？**A2A**（Agent2Agent Protocol）管身份如何声明、任务如何委派。两者管不同方向的连接，不互斥；A2A 只是 Agent 间协作协议的一个例子。

MCP 已是事实标准（截至 2026 年 10 月），明天可能换名字——协议会换代；而契约那份清单（一个工具声明什么、检查什么、重复请求怎么算、返回什么）要一直交代下去。所以工程上把力气花在契约上：协议交给框架追，契约自己写。

一个工具上线前，契约四步默认不能省；computer use 这类非结构化动作至少保留幂等与错误返回，其余按场景裁剪。

| 步骤 | 做什么 | 失败时给什么 |
| --- | --- | --- |
| 声明（schema） | 参数类型、字段含义、可选范围写成结构 | 不合 schema 的调用根本不出门 |
| 参数校验 | 缺、错、越界的参数在此拦下 | 结构化错误加一句人话提示 |
| 幂等 | 同一个请求做两遍，对外部只留一个结果 | 把“网络抖动”和“订两张票”分开 |
| 错误返回 | 失败也是消息，不是异常 | `{"ok": false, "error", "hint"}` 写回上下文 |

幂等是工具的义务，重试是调用方的策略：订票接口若不能幂等，一次重试就多一张票。订票重试：第一次超时，重发可能订成两张；不重发又可能让用户白等。解法不在客户端硬扛，而在契约里加一个幂等键：同一件事重发时带同一个键，工具凭它认出是同一个请求。这是把幂等写进契约的理由。

schema 就是约束解码用的那份结构规则：同一份声明，生成时约束输出形状，调用时校验参数。参数校验只是验证门的第一道。工具结果写回的位置，是上下文五格之一。比校验更靠前的还有注册表：不该出现的工具，根本不给它注册——删除而非劝告。

工具还能更粗一档。**computer use**：不给逐动作的结构化接口，模型直接看屏幕、点按钮、填表单，把整台电脑当一个工具；契约四步在这里大半用不上。Anthropic 的 Computer Use、OpenAI 的 Operator 是这一族的代表。这一档粒度最粗、权限边界最宽。

## 错误即消息：失败走同一条路，循环还得会停

错误处理做得对不对，判据不是有没有 raise，而是异常有没有被捕获、格式化成观测写回上下文。抛异常本身不必然静默失败；没被捕获的异常才会中断循环。正确做法是把失败当作一条观测：写回上下文，让模型下一轮基于这条信息做新决策。工具失败走的是消息通道：一条格式化的消息，不是异常，和成功返回走同一条注入路径。这就是“错误即消息”的意思。

工具对非法参数报错，框架捕获了错误，却只记在内部、没写回模型的上下文——模型不知道失败这回事，对外只能说“机票已订好”。内部记着一步失败，对外一个字不提。这不是 bug，是默认行为。改法在动手第三站（只改四行）：失败不再 raise，改成返回 `{"ok": false, "error": "days=999 越界", "hint": "先跟用户确认天数"}`，同样校验，结果走另一条路。模型据此改了说法：“没订成：天数 999 超出允许范围（1-30），请确认天数。”错误即消息，不等于放弃校验。

光会失败还不够，还得会停。三种显式的停止信号，行话叫 stopReason：`end_turn`（模型判断任务完成）、`max_turns`（步数上限）、`error_budget`（连续失败超阈值）。没有停止机制的 Agent，常见两种结局：要么永远转下去，要么在某个不可逆动作上冲出去。循环层能管前一种：`max_turns` 防死循环、`error_budget` 防反复失败，`end_turn` 管正常完成；不可逆动作要靠权限与确认，停止信号管不了。

## RAG与记忆：取回与存留

§7 讲过五步链：切块入库、变成向量去检索、重排、写进检索内容格、带引用作答。那五步解决“怎么检索”；真正上线，工程上有几项问题绕不开。

索引怎么更新：文档改了、条文废了，索引不会自己跟上；索引跟着文档版本走，旧条文要下线。

权限怎么裁：过滤时机是设计决策——入库时裁，查询时也还要再裁一次；错误的时机会把“看不到的文档”漏进引用里。

检索质量怎么量（召回评估）：要“问题 → 该召回的片段”的对表，判对错便宜、能自动化；验证越便宜，质量越能被规模地量出来。

既然上下文能装更多了，为什么还要检索：装得下不等于找得到，也不等于装得起；两条路线各有各的账，物理代价和 token 配额都是硬约束。

四问之外，检索家族还有两条新线。**GraphRAG**：把资料抽成图谱、顺着关系多跳地查。**自适应检索**：让模型自己判断该不该查、缺什么再补什么。
四问共同的底层判断：检索是把装不下、装不起、找不着、装不久的部分移出上下文；移出去的每一片，都要能更新、能授权、能被评估。

上下文与记忆这一角色管的东西分三层——记忆不是模型与生俱来的，是系统替它存、按需装回的那一份。它的核心动作是上下文装配：把该给的组装进窗口。会话内状态（窗口状态、历史、信念 bₜ 的工程维护）是第一级，跨会话记忆（任务与进展的持久化）是第二级，个性化（偏好的沉淀与使用）是第三级。领域知识（检索索引）归在跨会话记忆这一级，RAG 是它的取用方式——存的地方在记忆这一级，用时取回来，落进五格里的检索内容那一格。三层依次展开：持久化才有个性化，个性化不是把聊天记录全存下来。

会话内这一级有一个关键设计（以动手节第四站为体验）：会话事件日志是唯一真源。模型见过的每一段上下文，日志里都有；反过来，日志记下的事，事后都查得出：fork（会话分叉，从某个检查点另开一支）、恢复、压缩、回放、审计，共享同一份事实。不要用内存里的“当前状态”当真源：崩溃、回放、审计、多客户端同步全都会断。静默失败之所以可怕，不是没被记录，而是记了却没人对照；第四站的 audit 函数，对照的就是会话日志与最终答复这两样。

记忆的工程问题三问：什么值得写、什么时候读回来、怎么忘。写什么，按上下文五格过筛，不是全量搬运。什么时候读回来，靠上下文装配按需取：每轮装配时先装当下要用的，装不下、装不起的部分交给检索；长上下文与检索各有物理代价，取舍看任务。如何忘，靠压缩、过期与删除三件机制；只增不减的记忆是负债。忘与删不只是技术问题，还是权限与合规问题。

这套分层还有一个更远的读法：状态、记忆与偏好从模型里搬到系统里——挪走的是认知的一部分，这个方向叫**认知外移**。挪出来的都摆在明面上：能更新、能审计，也能被修正。

## 什么时候不需要 Harness：先走决策梯

上 Agent 之前，先沿三级决策梯往下问。第一级：一次模型调用加检索能不能解决？能，就别套循环。第二级：步骤是不是固定的？固定就用普通代码把流程写死，模型只在需要判断的节点出力——路径写死、判断交给模型，出错能定位到节点，这叫工作流，不叫 Agent。第三级：任务是否需要模型自己决定下一步、调用工具、根据反馈改计划？需要，才轮到 Agent。

| 任务形状 | 用什么 | 为什么 |
| --- | --- | --- |
| 一次问答、改写、分类 | 单次模型调用，按需加检索 | 没有多步状态，循环只增加延迟与成本 |
| 步骤固定的流程 | 工作流：代码控制步骤，模型做节点判断 | 路径可预测，出错可定位 |
| 步骤不定、需要工具与反馈 | Agent：模型在循环里选动作 | 只有这时，自主才换来任务表现 |
| 失败不可逆、代价高 | 先补权限、回滚、人审，再谈自主 | 能力不是放权的理由 |

梯子之外还有两问兜底：失败可逆吗？成功定义了吗？失败不可逆、又还没有验收标准，先补护栏与评估，再谈自主。另有四种任务形状，本来就不需要完整 Harness：单轮问答（无工具、无状态）与固定脚本流程，前面表格点过名；一次性演示、不追长期可靠；还没定义清楚成功与失败（兜底第二问的事）。

判据很简单：模型外面不需要循环、记忆、工具、安全、评估，就不需要 Harness。每多一层编排，延迟、成本和失效面都乘上去；自主是用延迟与成本换任务表现，失效面是跟着涨的第三笔账，值不值，按梯子一级一级问下来。正确做法是从最小循环起步：模型调用加工具先跑通，再按失效点补。“先不上”，是先分清任务属性；需要时再按失效点补件，不按资历补。

## 动手：六站，前五站跑通最小系统

全程零 API key。用一个按剧本逐句回复的假模型，每个失败场景都确定可复现；真模型跑一百次，静默失败可能只出现三十次，你会归因于“模型抽风”，假模型让它每次都出现，你才能看清机制。看清之后换真模型，一个 OpenAI 兼容端点就能顶替，其余代码一行不动。1–5 站约 90 分钟。快线可以止步第三站（循环、静默失败、错误即消息已经跑过一遍），第 4–6 站回补（第六站排在 §17 动手节）。

第一站，让它跑起来：十几行代码，查天气，`max_steps=3` 而剧本只有两条，它自己就分两步走完。Agent 不是调一次模型，是循环调用模型。这就是 Harness 的内核。

第二站，让它失败一下：订 999 天的机票，工具用 `raise` 拒绝非法参数。看输出：内部记录一步失败，对外说“机票已订好”。静默失败是默认行为，不是哪家的 bug。

第三站，让报错回到模型那里：只改四行，失败返回结构化错误。同样校验，改的是结果走哪条路。模型这回如实说话：“没订成：天数 999 超出允许范围（1-30）。”这一站就是前面“错误即消息”那节的现场证据。

第四站，打开日志：写一个 audit 函数，对照 `memory.steps` 会话日志与最终答复。二站的 agent 重跑一遍，审计报出“不一致：1 步失败，但答复没提”。日志在那，缺的是对照。这就是评估与观测这一角色的雏形。

第五站，用 AI 搭最小系统：要一个循环、一个工具注册表、一个事件日志，别让它一次写完。分三轮，每轮验收：先跑通循环；再加日志，每次工具调用及结果都记在账上；最后加护栏，跑 999 天场景，审计又抓住一次不一致——这一站的剧本让模型连试两次，两次都被工具拒下，账上记成“2 步失败，但答复没提”。三种最常见的错法：`while True` 不设上限，模型一直调工具就死循环；工具报错用 `raise`，错误进不了上下文；用全局变量存状态，换个任务就互相污染。发现报错时别说“写得不对”：把报错原样贴回去——第三站的教训，错误要经过完整路径回到模型。

代码与运行记录在 `assets/§16-体验实验/`：假模型按固定剧本逐句回复；第五站最小系统照参考实现落盘，参数解析处有一处最小修正，试跑的失败记录与修正理由同目录留档。依赖：Python 3.11 以上，`pip install smolagents`。前四站借 smolagents 这个开源框架的 CodeAgent 当循环，把按剧本回复的假模型接进去；第五站的参考实现不用框架，循环、注册表、日志是手写的十几行。各站脚本用 `python3 stationN.py` 直接运行（零密钥）。

## 回望与下一章

模型之外的东西已经成套：一个循环、六件事、协议与契约、数据流、停止信号，每件是什么、缺了会怎样，表里都对得上。循环靠数据流运转：上下文与记忆守着 bₜ，工具执行动作，错误走观测通道，编排管三种停止信号（end_turn／max_turns／error_budget），评估与护栏横切每一步。六件事是分工，不是层级；上不上 Agent，先走决策梯，从最小循环起步。

1. 一个 Agent 的最小形状是什么，六件事各管什么？
2. 工具调用的最小契约四步各防什么失败？
3. 什么情况下先不上 Agent？

<details>
<summary>答案与去处</summary>

1. 最小形状是一个循环：模型读上下文选动作，系统执行并把结果写回，循环到停止为止。六件事：模型调用、工具与协议、上下文与记忆、编排、评估与观测、护栏与权限；评估与护栏横切每一步，不在顶上；简单任务模型调用加工具就够。回看：“最小形状”与“数据流循环”。
2. 声明（schema）拦不合结构的调用；校验拦缺、错、越界；幂等防重试多订一张票；错误返回把失败写回上下文。错误即消息是把失败当观测，不是不校验：校验仍在，失败走消息通道，模型下一轮才能改。回看：“工具调用的最小契约”与“错误即消息”。
3. 先问一次调用加检索够不够，再问步骤是否固定、该走工作流，最后问是否真需要模型自主决定路径；失败不可逆或成功没定义时，先补护栏与评估。回看：“什么时候不需要 Harness”。
