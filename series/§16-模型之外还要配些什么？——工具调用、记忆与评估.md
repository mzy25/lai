# §16 模型之外还要配些什么？——工具调用、记忆与评估 ▽

模型在真实任务里出错，问题常在系统结构，补也要从结构入手。能力之外，模型还要配哪些工程组件？这些组件如何连接、如何检查、运行时会怎样失效？先列组件，再画连接，然后看运行，最后把整套系统亲手跑五站。

给“模型外面的工程系统”一个名字：**Harness**。这里取它在工程里的用法：把模型能力接到任务上的外围系统。模型更聪明一分，系统上的缺口不会因此消失。

## Harness 六层：模型的外围

一份流传很广的组件清单把智能体拆成四样：语言模型（推理）、规划、记忆、工具使用。四样只列组件，不给连接方式，也不给质检流程；而生产级 Agent 的可靠性，恰恰来自连接和质检，不只是组件本身。按生产系统的分工，可以把它补成六层。四组件拆法常追溯到 Weng 2023；六层结构图与 Perrone 2026 的分层相近，此处按问题链重排：

| 层 | 管什么 | 一个工程动作 |
| --- | --- | --- |
| L1 推理 | 调用模型完成理解与决策 | 接任何 OpenAI 兼容端点 |
| L2 协议与工具 | 经 MCP、A2A 等协议调用外部 API、浏览器与代码执行器 | 注册一个带 schema 的工具 |
| L3 记忆与知识 | 存取窗口状态、历史、偏好与领域知识 | 把会话事件日志写进上下文 |
| L4 编排 | 组合模型调用、工具使用和控制流 | 决定何时重试、何时中断 |
| L5 评估与可观测 | 追踪执行轨迹、评分输出、捕捉退化 | 让每一步可回放、可打分 |
| L6 护栏与安全 | 过滤输入、授权工具调用、验证输出 | 给一个动作过一道安全的门 |

〔图 16-1：Harness 六层——六层全在模型外面，每层一个工程动作。〕

七元组与六层的关系一句话说完：§15 的信念状态 bₜ 由 L3 维护，工具的调用与返回是 Agent 的观测，七元组是流程的数学模型，六层是它的工程组件表。两套视角回答同一个问题：Agent 怎么转起来。

现状（按公开实现的通行分层，截至 2026 年 10 月）：L1、L2 已有可依赖的方案，L3 记忆与 L4 编排仍各有功课，真正的缺口在 L5 评估与 L6 护栏：护栏怎么守，见 §17；评估器怎么自立门户，见 §19。把六层当推荐架构、不当标准答案来读：少任何一层，系统就在对应环节多一种失效方式：没有 L5，你不知道 Agent 第几步走偏；没有 L6，Agent 调用的工具可能已经造成不可逆的伤害。简单的单步任务，L1 加 L2 足够。

一个开源实例：Pi（github.com/earendil-works/pi）把这套分层落成了代码，六层各有明确模块（截至 2026 年 10 月，仓库活跃）。

两个常见误解。"六层是模型架构"这句错在：六层全在模型外面，不是模型内部结构。"六层是成熟度阶梯"也反了：六层是结构图不是排行榜，按失效点补层，不讲资历。

## 协议层：协议会换代、契约不变

工具怎么接到模型上？先分清两样东西。协议是信道与握手规范，会换代；契约是工具自己的义务清单，换协议换不掉。**MCP**（Model Context Protocol，模型上下文协议）管 Agent 与工具之间怎么连接：工具如何声明能力、参数如何校验、返回值如何结构化。Agent 与 Agent 之间怎么协作？**A2A**（Agent2Agent Protocol）管身份如何声明、任务如何委派。两者管不同方向的连接，不互斥，A2A 是其中的一个例子。

MCP 已是事实标准（截至 2026 年 10 月），明天可能换名字——协议会换代；而契约那份清单（一个工具声明什么、检查什么、重复请求怎么算、返回什么）要一直交代下去。所以工程上把力气花在契约上：协议交给框架追，契约自己写。

## 数据流循环

六层怎么转起来？把一个回路画成一条箭头链：

    oₜ —L3 记忆→ bₜ —L1 推理→ aₜ —L2 工具→ oₜ₊₁

四个符号各是什么。oₜ 是观测，用户输入、工具返回、报错，都是模型能看到的东西；bₜ 是信念状态，就是 §15 手算的那张分配表，由 L3 记忆维护；aₜ 是动作，搜索、写代码、调 API，由 L2 工具执行（aₜ 的 a 是动作 action，与支线里那个 a_t 不是一回事）；oₜ₊₁ 是新观测，动作之后的下一轮。

L4 编排不在箭头链上：它是控制整个循环节奏的那一层，何时调用模型、何时重试、何时中断、何时升级给人。

〔图 16-2：Agent Loop 运行时剖面——内层四盒的箭头链与三种停止信号；示意图，非实测。〕

一个编码 Agent 修 bug，第三轮的表长这样（教学推演，表内阈值与文件名均为设定）：

| 层 | 这一轮做什么 | 具体数据 |
| --- | --- | --- |
| L5 | 读出测试失败 | `failed test_parse_date` |
| L3 | 组装上下文 | 任务、失败计数、最近一次改动 |
| L1 | 判断病因 | 是日期格式串写错 |
| L6 | 过安全门 | 风险 0.2，低于示例阈值 0.7，放行 |
| L2 | 执行改动 | `edit_file(utils.py, 格式串)` |
| L4 | 调度下一轮 | 重跑测试 |

表里的 0.7 是示例阈值，A_safe(c)（安全动作集合）的完整形态见 §17。一个反例：如果 L3 丢了历史，忘了第一轮已经改过格式串，L1 可能再改一次。循环在原地转，两轮白跑。

## 错误即消息：失败的返回值走同一条路

朴素做法是抛异常、中断循环。正确做法是把失败当作一条观测：写回上下文，让模型下一轮基于这条信息做新决策。工具失败走的是消息通道：一条格式化的消息，不是异常，和成功返回走同一条注入路径。这就是"错误即消息"的意思。

动手节第二站就是现成的例子：工具对非法参数报错，框架捕获了错误，模型对外却说"机票已订好"。内部记着一步失败，对外一个字不提。这不是 bug，是默认行为。第三站只改四行：失败不再 raise，改成返回 `{"ok": false, "error": "days=999 越界", "hint": "先跟用户确认天数"}`，同样校验，结果走另一条路。模型据此改了说法："没订成：天数 999 超出允许范围（1-30），请确认天数。"错误即消息，不等于放弃校验。

光会失败还不够，还得会停。三种显式的停止信号，行话叫 stopReason：`end_turn`（模型判断任务完成）、`max_turns`（步数上限）、`error_budget`（连续失败超阈值）。没有停止机制的 Agent，要么永远转下去，要么在某个不可逆动作上冲出去。防死循环和防失控是两件事，得设两层停止机制。

## 工具调用的最小契约：声明、校验、幂等、返回 ▽

一个工具上线前，契约四步，一步不能省。

| 步骤 | 做什么 | 失败时给什么 |
| --- | --- | --- |
| 声明（schema） | 参数类型、字段含义、可选范围写成结构 | 不合 schema 的调用根本不出门 |
| 参数校验 | 缺、错、越界的参数在此拦下 | 结构化错误加一句人话提示 |
| 幂等 | 同一个请求做两遍，对外部只留一个结果 | 把"网络抖动"和"订两张票"分开 |
| 错误返回 | 失败也是消息，不是异常 | `{"ok": false, "error", "hint"}` 写回上下文 |

幂等是工具的义务，重试是调用方的策略：订票接口若不能幂等，一次重试就多一张票。订票重试：第一次超时，重发可能订成两张；不重发又可能让用户白等。解法不在客户端硬扛，而在契约里加一个幂等键：同一件事重发时带同一个键，工具凭它认出是同一个请求。这是把幂等写进契约的理由。

schema 就是约束解码用的那份结构规则：同一份声明，生成时约束输出形状，调用时校验参数。参数校验只是验证门的第一道；完整的验证门与理论出处见 §17。工具结果写回的位置，是上下文五格之一。比校验更靠前的还有注册表：不该出现的工具，根本不给它注册——删除而非劝告；这道门见 §17。

工具还能更粗一档。**computer use**：不给逐动作的结构化接口，模型直接看屏幕、点按钮、填表单，把整台电脑当一个工具；契约四步在这里大半用不上。Anthropic 的 Computer Use、OpenAI 的 Operator 是这一族的代表。这一档粒度最粗、权限边界最宽，安全边界见 §17。

## RAG：上线要回答的问题

§7 讲过五步链：切块入库、变成向量去检索、重排、写进检索内容格、带引用作答。那五步解决"怎么检索"；真正上线，工程上有几项问题绕不开。

索引怎么更新：文档改了、条文废了，索引不会自己跟上；索引跟着文档版本走，旧条文要下线。

权限怎么裁：过滤时机是设计决策——入库时裁，查询时也还要再裁一次；错误的时机会把"看不到的文档"漏进引用里（安全边界见 §17）。

检索质量怎么量（召回评估）：要"问题 → 该召回的片段"的对表，判对错便宜，能自动化，这正是 §14 可验证性剃刀的用法。

既然上下文能装更多了，为什么还要检索：装得下不等于找得到，也不等于装得起；两条路线各有各的账（§18 细算），物理代价和 token 配额都是硬约束。

四问之外，检索家族还有两条新线。**GraphRAG**：把资料抽成图谱、顺着关系多跳地查。**自适应检索**：让模型自己判断该不该查、缺什么再补什么。两条各留一句，用到再展开。

四问共同的底层判断：检索是把装不下、装不起、装不久的部分移出上下文；移出去的每一片，都要能更新、能授权、能被评估。

## 状态与记忆：分层与追问

L3 管的东西分三层。L3 的核心动作是上下文装配：把该给的组装进窗口。会话内状态（窗口状态、历史、信念 bₜ 的工程维护）是第一级，跨会话记忆（任务与进展的持久化）是第二级，个性化（偏好的沉淀与使用）是第三级。三层依次展开：持久化才有个性化，个性化不是把聊天记录全存下来。

会话内这一级有一个关键设计（以动手节第四站为体验）：会话事件日志是唯一真源。模型见过的每一段上下文，日志里都有；反过来，日志记下的事，事后都查得出：fork、恢复、压缩、回放、审计，共享同一份事实。不要用内存里的"当前状态"当真源：崩溃、回放、审计、多客户端同步全都会断。静默失败之所以可怕，不是没被记录，而是记了却没人对照；第四站的 audit 函数，对照的就是会话日志与最终答复这两样。

记忆的工程问题三问：什么值得写、什么时候读回来、怎么忘。写什么，按上下文五格过筛，不是全量搬运。什么时候读回来，靠上下文装配按需取：每轮装配时先装当下要用的，装不下、装不起的部分交给检索；长上下文与检索各有物理代价，取舍看任务。如何忘，靠压缩、过期与删除三件机制；只增不减的记忆是负债。忘与删不只是技术问题，还是权限与合规问题。

这套台阶还有一个更远的读法：状态、记忆与偏好从模型里搬到系统里——挪走的是认知的一部分，这个方向叫**认知外移**。挪出来的都摆在明面上：能更新、能审计，也能被修正。

## 什么时候不需要 Harness

四种情况，先不要上完整 Harness。单轮问答、无工具、无状态：直接调模型接口即可。固定脚本流程、不需要模型自主决策：用普通代码控制流程更简单。只做一次性演示、不追求长期可靠：可以先不建日志、评估与护栏。还没定义清楚"成功"和"失败"：先补评估指标，再考虑 Harness。

判据很简单：模型外面不需要循环、记忆、工具、安全、评估，就不需要 Harness。能用一次模型调用解决的事，不要套循环：每多一层编排，延迟、成本和失效面都乘上去。正确做法是从最小循环起步：L1 加 L2 先跑通，再按失效点逐层补。"先不上"，是先分清任务属性；需要时再按失效点补层。

## 动手：六站，前五站跑通最小系统

全程零 API key。用一个按剧本逐句回复的假模型，每个失败场景都确定可复现；真模型跑一百次，静默失败可能只出现三十次，你会归因于"模型抽风"，假模型让它每次都出现，你才能看清机制。看清之后换真模型，一个 OpenAI 兼容端点就能顶替，其余代码一行不动。1–5 站约 90 分钟，第六站见 §17。快线可以止步第三站（循环、静默失败、错误即消息已经撞过一遍），第 4–6 站回补。

第一站，让它跑起来：十几行代码，查天气，`max_steps=3` 而剧本只有两条，它自己就分两步走完。Agent 不是调一次模型，是循环调用模型。这就是 Harness 的内核。

第二站，让它失败一下：订 999 天的机票，工具用 `raise` 拒绝非法参数。看输出：内部记录一步失败，对外说"机票已订好"。静默失败是默认行为，不是哪家的 bug。

第三站，让报错回到模型那里：只改四行，失败返回结构化错误。同样校验，改的是结果走哪条路。模型这回如实说话："没订成：天数 999 超出允许范围（1-30）。"这一站就是前面"错误即消息"那节的现场证据。

第四站，打开日志：写一个 audit 函数，对照 `memory.steps` 会话日志与最终答复。二站的 agent 重跑一遍，审计报出"不一致：1 步失败，但答复没提"。日志在那，缺的是对照。这就是 L5 评估的雏形。

第五站，用 AI 搭最小系统：要一个循环、一个工具注册表、一个事件日志，别让它一次写完。分三轮，每轮验收：先跑通循环；再加日志，每次工具调用及结果都记在账上；最后加护栏，跑 999 天场景，审计又抓住一次不一致（"2 步失败，但答复没提"）。三种最常见的错法：`while True` 不设上限，模型一直调工具就死循环；工具报错用 `raise`，错误进不了上下文；用全局变量存状态，换个任务就串味。发现报错时别说"写得不对"：把报错原样贴回去——第三站的教训，错误要经过完整路径回到模型。

代码与运行记录在 `assets/§16-体验实验/`：假模型按固定剧本逐句回复；第五站最小系统照参考实现落盘，参数解析处有一处最小修正，试跑的失败记录与修正理由同目录留档。依赖一行：Python 3.11 以上，`pip install smolagents`；各站脚本用 `python3 stationN.py` 直接运行（零密钥）。
