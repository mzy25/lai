# §18 一个大目标，怎样拆成能落地、也能反悔的步骤？——规划、成本与实施 ▽

控制权定下之后，下一步是把模糊目标落成可执行步骤，并算清每一步的账。机器拿到目标，先别动手，先把目标拆开。拆法有四种主流形态，拆得好不好有四个诊断维度，成熟的经验能固化成技能包，每一步还要付钱。

规划不是让模型想得更久。思维链是模型自己写出的推理过程，规划是模型外面的一套结构：步骤、依赖、回滚点、谁确认，都搭在模型外面——模型只在结构里出力。规划也不是越复杂越好：四种形态各有适用场景，拆到能落地、能回滚就够。

## 规划形态与判据

工业界收敛出四种规划形态，覆盖不同场景，不是互相取代。

| 形态 | 结构 | 修正机制 | 典型场景 | 相对成本 |
| --- | --- | --- | --- | --- |
| 反应式（ReAct） | 走一步看一步 | 每步基于反馈自省 | 探索式任务、工具链短 | 低 |
| 先规划后执行（Plan-and-Execute） | 一次画完步骤图再跑 | 全跑完再评估 | 步骤明确、上下文长 | 中 |
| 树搜索（ToT/LATS） | 多路并行＋剪枝 | 分支择优、回溯 | 高价值决策、可回滚 | 高 |
| 反思迭代（Reflexion） | 跑完打分再重跑 | 事后总结进记忆 | 有明确成功判据 | 更高 |

四种形态的区别，在于"想"与"做"的组合比例不同：反应式当场决定，先规划后执行把想前置，树搜索同时想好几条（剪枝是砍掉没前途的分支，回溯是失败后另找一条路），反思迭代让想发生在失败之后（跑完一轮，总结教训，带进下一轮）。成本低不等于初级，选型只看场景，判据三条：可回滚性看任务做错了能不能退回上一步，决定要不要树搜索；上下文够不够装下整个规划，决定用反应式还是先规划后执行；成功信号明不明确，决定要不要反思闭环。真实产品往往混用：主循环走反应式，遇到复杂任务切成先规划后执行，测试失败触发反思。

经典规划问题里有 NP-hard 的硬骨头，精确求解在最坏情况下指数爆炸；学习型规划换了一条路，学的是"典型情形够好"的启发式，不是最坏情形的最优保证。所以规划质量要按场景问，不能拿最坏情况一票否决，也不能把启发式当保证。

## APB：把规划质量拆成诊断维度

Agent Planning Benchmark（APB，Sun 等 2026）把规划评估往前推了一步：不再问哪种形态更强，问规划的哪个子能力有短板。它收集 4,209 个多模态规划任务，横跨 22 个领域，覆盖 5 种设定，在 12 个前沿模型上测出四个维度的系统性短板（数据来自论文摘要，截至 2026 年 10 月）。

| 维度 | 典型失败 | 工程手段 |
| --- | --- | --- |
| D1 长程规划 | 任务展开几十步后，Agent 忘了自己在走哪条路 | 规划前置成图，关键步骤设检查点 |
| D2 工具鲁棒 | 被无关工具吸引，对损坏工具反复重试 | 只暴露相关工具子集，失败快速降级 |
| D3 校准拒绝 | 任务不可解时硬凑一个看起来对的方案 | 允许"任务无法完成"作为显式终止状态 |
| D4 推理时精化 | 每步都在给上一步的错误打补丁 | 设重规划触发条件，超阈值从当前状态重画 |

这四个是论文观察到的薄弱维度，不是基准的四个正式任务分区。基准自己还分了整体规划、分步规划、加干扰工具、坏工具、不可解任务等设定。APB 的价值是把规划质量从端到端成功率里剥出来：以前只能说"这个 Agent 失败了"，现在能定位到它在长程规划维度上失败了，就像程序员先写单元测试：把程序拆成小块，一块一块测；再把"程序跑挂了"定位到具体模块。编程 Agent 是这套诊断现成的对象——你可以按 APB 的设定逐项体检。

## 技能包与渐进披露

规划模式是可复用的资产。同类任务每次重新规划一遍都是浪费：处理表单填充、跨仓库搜代码、按品牌规范生成文档，这些流程有稳定结构。Agent Skills 把稳定规划模式固化成技能包：一个 skill 是一个含 SKILL.md 的目录，装指令、脚本、资源三类内容。

核心设计是渐进披露，分三层加载：启动时只把每个 skill 的名字和几十字描述放进上下文；模型判断某个 skill 相关，才把完整 SKILL.md 读进来；SKILL.md 引用的附加文件，真正用到时才读。三层懒加载让技能库容量可以很大，上下文预算始终受控。技能也有跨平台的标准格式（agentskills.io，截至 2026 年 10 月），一个 skill 能在多个 Agent 平台之间迁移。

技能包也有代价。第一，库越大选错越多：库扩容之后，第一反应常是"上下文开销变大"；真正的麻烦却在选择——选错 skill 的情况变多了。库里还会出现容量临界点，越过之后选择精度骤降。第二，僵化 skill 会帮倒忙：环境反馈带宽高的任务里，有些加了 skill 反而变差——工具层反馈严格快速时，环境自己就在教模型，skill 的边际收益塌缩。成套的应对：渐进披露管装多少，检索前置管选得准，层次化收纳管分得清，容量上限加淘汰管长不大；反馈带宽高的场景少用 skill，让环境说话。库无节制增长会退化（Library Drift）。装、选、收、汰，四件事各有闸门。

## 成本账、自建还是买 API

Agent 的成本乘数账：一个任务的成本乘数约等于步数 × 每步调用次数 × 每步调用的 token。分支越多、链越长、失败重跑，各个因子逐个乘上去，同样一个任务的账单能差出好几个量级。这些数字是设定算例，真实价格会随时间浮动。成本分三笔账。

第一笔是模型账单，按调用次数与 token 走：多档思考、并行采样、失败重跑，都在这一笔上相乘。

第二笔是基础设施账。上下文不是免费的：长上下文把全部历史塞进窗口，每步输入的 token 随步数线性涨（总账按步数累加是二次量），KV 缓存和 token 配额都是硬约束。检索把"装得下"换成"找得到、装得起"：索引、存储、查询也各有成本。长上下文和检索这两条路各有各的账，取舍看任务——窗口装得下、又不常翻旧账，长上下文省心；任务多、历史长，检索的基础设施摊得薄。

第三笔是自建还是 API 的决策账：成本轴看调用量与折扣，固定成本能否摊薄；数据隐私轴看数据能不能出域、日志留在谁手里；可控可审计轴看路由、版本、回放、定制谁说了算。换算只有一条规矩：调用量稳定、数据不出域，就把自建的固定成本摊进单价来比；量小、波动大、要快，API 的即开即用更省。三个轴没有默认赢家，按场景权衡。

把模型压小送进端侧，靠蒸馏与量化两条线：蒸馏把大模型的本事搬进小模型，量化把权重压到 4-bit；密度定律说，够用的模型还在变小。合起来，小模型加 4-bit 量化部署，成了低成本部署的主路。推理成本这几年持续下降。推理预算按任务难度分配：简单步骤走低档，少花 token；关键分支走高挡，让模型多想。产品通常按难度分档。

## 动手：给前五站 Agent 估月成本

把前五站搭起的 Agent 从假模型换成真模型，估它一个月的账单。四个档位各估一遍：模型直接答；反应式多步；反应式加三路探索；再加反思重跑。

参数自己填：月任务数、每任务步数、每步调用次数、平均输入输出 token、模型输入输出单价（记查价日期与模型名）、探索分支数、重跑次数、基础设施固定成本。不设示例价；价格随模型和日期变化，按你查到的价填。

交付三样：一张四档成本表，每个金额都能用"调用次数 × token × 单价 ＋ 固定成本"复算；一段自建还是 API 的三轴判断；一条敏感性结论：哪个乘数动一动，账单变化最大。验收标准：设定与现实价格分列、假设写明、结论不伪装成采购建议。

## 回望与下一章

规划这条线从形态走到落成：这些形态按可回滚性、上下文、成功信号选型；APB 把规划质量拆成诊断维度，工程手段逐维度对应；技能包固化稳定流程，靠渐进披露和容量治理把代价管住。成本账：模型账单、基础设施账、自建决策账，决定这条闭环跑不跑得起；推理预算花在值得的分支上。

三题自查。

1. 四种规划形态各是什么结构、修正机制和适用场景？三条判据各决定哪种形态的取舍？
2. APB 的四个诊断维度各是什么，对应的工程手段是什么？为什么说四个维度不是基准的四个正式分区？
3. 成本账各自由什么驱动？如果让你给前五站 Agent 估月成本，你会先抓哪三个参数？

规划完备，闭环也能跑，实战里 Agent 还是会成群地翻车。一群智能体一起干活，会多出什么？
