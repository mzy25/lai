# §18 一个大目标，怎样拆成能落地、也能反悔的步骤？——规划、成本与实施 ▽

控制权定下之后，下一步是把模糊目标落成可执行步骤，并算清每一步的账。系统拿到目标，先把目标拆开，再动手。拆法有四种主流形态（选型看三条判据），拆得好不好另有四个诊断维度（一个规划基准的体检账，名字在 APB 一节给全），成熟的经验能固化成技能包；任务长过一次会话时，还要把目标、进度与验收落到模型外面的文件里；每一步还要付钱。

规划是模型外面的一套结构：步骤、依赖、回滚点、谁确认，都搭在模型外面——模型只在结构里出力。思维链是模型自己写出的推理过程，两者不是一回事。规划也不是越复杂越好：四种形态各有适用场景，拆到能落地、能回滚就够。

## 规划形态与判据

工业界收敛出四种规划形态，覆盖不同场景，不是互相取代。

| 形态 | 结构 | 修正机制 | 典型场景 | 相对成本 |
| --- | --- | --- | --- | --- |
| 反应式（ReAct） | 走一步看一步 | 每步基于反馈自省 | 探索式任务、工具链短 | 低 |
| 先规划后执行（Plan-and-Execute） | 一次画完步骤图再跑 | 全跑完再评估 | 步骤明确、规划装得下窗口 | 中 |
| 树搜索（ToT/LATS） | 多路并行＋剪枝 | 分支择优、回溯 | 高价值决策、可回滚 | 高 |
| 反思迭代（Reflexion） | 跑完打分再重跑 | 事后总结进记忆 | 有明确成功判据 | 更高 |

四种形态的区别，在于“想”与“做”的组合比例不同：反应式当场决定，先规划后执行把想前置，树搜索同时想好几条（剪枝是删掉价值低的分支，回溯是失败后另找一条路），反思迭代让想发生在失败之后（跑完一轮，总结教训，带进下一轮）。成本低不等于初级，选型只看场景，判据三条：可回滚性看任务做错了能不能退回上一步，决定要不要树搜索；上下文够不够装下整个规划，决定用反应式还是先规划后执行；成功信号明不明确，决定要不要反思闭环。真实产品往往混用：主循环走反应式，遇到复杂任务切成先规划后执行，测试失败触发反思。

拿一个具体目标走一遍：“给客服系统接退款 Agent”。先列步骤：读订单 → 核对身份 → 查退款政策 → 执行退款 → 写回执；再标依赖（验身份在退款前）、回滚点（退款前可撤回，退款后只能补偿）、确认人（超额或异常单转人工）。步骤、依赖、回滚点、确认人四样凑齐，这张清单就是一张步骤图（这里是单链）；换反应式，就把它拆成每步一问，走一步看一步。

经典规划问题（如积木世界这类规划任务）里有 NP-hard 的硬骨头，精确求解在最坏情况下指数爆炸；学习型规划换了一条路，学的是“典型情形够好”的启发式，不是最坏情形的最优保证。所以规划质量要按场景问，不能拿最坏情况一票否决，也不能把启发式当保证。

## APB：把规划质量拆成诊断维度

Agent Planning Benchmark（APB，Sun 等 2026）把规划评估往前推了一步：不再问哪种形态更强，问规划的哪个子能力有短板。它收集 4,209 个多模态规划任务，横跨 22 个领域，覆盖 5 种设定，在 12 个前沿模型上测出四个维度的系统性短板（数据来自论文摘要，截至 2026 年 10 月）。

| 维度 | 典型失败 | 工程手段 |
| --- | --- | --- |
| D1 长程规划 | 任务展开几十步后，Agent 忘了自己在走哪条路 | 规划前置成图，关键步骤设检查点 |
| D2 工具鲁棒 | 被无关工具吸引，对损坏工具反复重试 | 只暴露相关工具子集，失败快速降级 |
| D3 校准拒绝 | 任务不可解时硬凑一个看起来对的方案 | 允许“任务无法完成”作为显式终止状态 |
| D4 推理时精化 | 每步都在给上一步的错误打补丁 | 设重规划触发条件，超阈值从当前状态重画 |

这四个是论文观察到的薄弱维度，不是基准的四个正式任务分区。基准自己还分了整体规划、分步规划、加干扰工具、坏工具、不可解任务等设定。APB 的价值是把规划质量从端到端成功率里剥出来：以前只能说“这个 Agent 失败了”，现在能给出分维度证据；至于这个维度是不是端到端失败的主因，还要靠消融（逐项关掉某个部件、看指标掉多少）或日志验证。就像程序员先写单元测试：把程序拆成小块，一块一块测；再把“程序跑挂了”定位到具体模块。拿一个编程 Agent 来，就是这套诊断现成的对象——按这四个维度逐项体检。

## 技能包与渐进披露

规划模式是可复用的资产。同类任务每次重新规划一遍都是浪费：处理表单填充、跨仓库搜代码、按品牌规范生成文档，这些流程有稳定结构。Agent Skills 把稳定规划模式固化成技能包：一个 skill 是一个含 SKILL.md（技能的说明书，平台按这个文件名认技能）的目录，装指令、脚本、资源三类内容。

核心设计是渐进披露，分三层懒加载（用到哪层才把哪层读进来）：启动时只把每个 skill 的名字和几十字描述放进上下文；模型判断某个 skill 相关，才把完整 SKILL.md 读进来；SKILL.md 引用的附加文件，真正用到时才读。三层懒加载让技能库容量可以很大，加载阶段上下文受控；但选择精度与描述开销随库增长，容量仍有上限。技能也有跨平台的标准格式（agentskills.io，截至 2026 年 10 月），一个 skill 能在多个 Agent 平台之间迁移。

技能包也有代价。第一，库越大选错越多：库扩容之后，第一反应常是“上下文开销变大”；真正的麻烦却在选择——选错 skill 的情况变多了。库里还会出现容量临界点，越过之后选择精度骤降（经验观察，不是定理）。第二，僵化 skill 会帮倒忙：环境反馈带宽高（每步反馈又快又具体）的任务里，有些加了 skill 反而变差——工具层反馈严格快速时，环境反馈本身就在教模型，skill 的边际收益塌缩。成套的应对：渐进披露管装多少，检索前置管选得准，层次化收纳管分得清，容量上限加淘汰管长不大；反馈带宽高的场景少用 skill，让环境反馈直接起作用。库无节制增长会退化（Library Drift）。装、选、收、汰，四件事各有闸门。

## 长任务：把一次会话做成可交接的工程

任务一旦长过一次会话，问题的形状就变了：模型自己没有跨会话的记忆——§16 说的“记忆”是系统替它记的那一份——每个新会话都从零开始。长任务要解的不是“更聪明”，是“交接”——把目标、进度与验收写成模型外面的文件，让下一个会话接得上。

一套公开的工程配方（Anthropic 的长任务 harness 实践报告，2025 年 11 月；以编码 Agent 为例）分四件。特性清单：把大目标拆成一条条可验收的特性，写成机器可读的清单，红线写死（比如不许删测试）。一次只做一件：每个会话只推进一条特性，做完就提交，不贪多。进度落盘：每一步用版本控制留一个可回退的存档点，进度文件记三样——做完什么、下一步是什么、卡在哪。自测如真实用户：改完不是问模型“好了吗”，而是自己真去用一遍——打开页面、点按钮、看结果。新会话开工的第一件事，就是把清单和进度文件读进来。

四种典型失败，对照配方就能诊断：一口气做完不提交，中途崩了无法回退；没过自测就宣布完成；留下改到一半的脏状态污染下一步；清单丢了，新会话不知道还剩什么。这四样都不是模型能力问题，是交接工程缺了件。三件对四种失败正好接上：清单防第四种，进度防第一种与第三种，验收防第二种。

配方不绑定编码。换成写方案、做调研这类非编码任务，取三件就够（编码版四件里的“一次只做一件”并进了进度这一件）：清单（目标拆成可验收条目）、进度（一次只推进一条，每步记做了什么、接下来做什么、卡在哪，随手留一份可回退的存档）、验收（每条做完真去检查）。用不用版本控制不重要，重要的是三样都落在模型外面——与 §16 的会话事件日志同一思路：唯一真源在文件里，不在内存里。会话崩了、换人接手、明天再来，都接得上。

## 成本账、自建还是买 API

Agent 的用量账：一个任务的 token 用量约等于步数 × 每步调用次数 × 每步调用的 token，三样都按平均估。长上下文里每步输入还会随步数涨，那笔账记在下面第二笔里：先按平均估月成本，跑长任务再补这笔；金额 = 用量 × 单价 ＋ 固定成本，单价输入、输出各一个，分开乘再相加。先抓的三个乘数是：每任务步数、每步调用次数、每步 token。分支越多、链越长、失败重跑，各个因子逐个乘上去，同样一个任务的账单能差出好几个量级。三个乘数只是设定框架，真实价格会随时间浮动。成本分三笔账。

第一笔是模型账单，按调用次数与 token 走：多档思考（按难度选不同推理档位）、并行采样、失败重跑，都在这一笔上相乘。

第二笔是基础设施账。上下文不是免费的：长上下文把全部历史塞进窗口，每步输入的 token 随步数线性涨（第 k 步带着约 k 步的历史，1+2+…+n 加起来，总账按步数平方涨），KV 缓存和 token 配额都是硬约束。检索把“装得下”换成“找得到、装得起”：索引、存储、查询也各有成本。长上下文和检索这两条路各有各的账，取舍看任务——窗口装得下、又不常翻旧账，长上下文省心；任务多、历史长，检索的基础设施摊得薄。

第三笔是自建还是 API 的决策账。先判数据隐私/合规是不是硬约束：数据不能出域，API 直接出局，不必再比成本。硬约束过关后，再比两根轴——成本轴看调用量与折扣、固定成本能否摊薄；可控可审计轴看路由、版本、回放、定制由谁决定。换算的规矩：合规过关、数据可出域时，调用量稳定就把自建的固定成本摊进单价来比；量小、波动大、要快，API 的即开即用更省。两根轴没有默认赢家；隐私合规是前置门槛，按场景权衡。

把模型压小送进端侧，靠蒸馏与量化两条线：蒸馏把大模型的本事搬进小模型，量化把权重压到 4-bit；密度定律说，够用的模型还在变小。合起来，小模型加 4-bit 量化部署，成了低成本部署的主路。推理成本这几年持续下降。推理预算按难度分档：简单步骤走低档，关键分支走高档。怎么判一个分支值不值得高档，看两样——这一步错了，后面的步骤要不要跟着重来；这一步的输出，后面几步是不是都要用。错了要重来、人人要用的，走高档；独立又可逆的，走低档。

## 动手：给前五站 Agent 估月成本

把前五站搭起的 Agent（§16 动手的前五站）从假模型换成真模型，估它一个月的账单。四个成本档位各估一遍：模型直接答；反应式多步；反应式加三路探索；再加反思重跑。

参数自己填：月任务数、每任务步数、每步调用次数、平均输入输出 token、模型输入输出单价（记查价日期与模型名）、探索分支数、重跑次数、基础设施固定成本。不设示例价；价格随模型和日期变化，按你查到的价填。

交付三样：一张四档成本表，每个金额都能用“调用次数 × token × 单价 ＋ 固定成本”复算；一段自建还是 API 的两轴判断（隐私合规单列硬门槛）；一条敏感性结论：哪个乘数动一动，账单变化最大。验收标准：设定与现实价格分列、假设写明、结论不伪装成采购建议。
